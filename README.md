# CRM-lite — агентство выставочных стендов

Локальная CRM-lite для агентства, которое проектирует и строит выставочные
стенды, выставочные пространства и бренд-зоны. Полный стек: Next.js (App
Router) + PostgreSQL + Prisma, без внешних SaaS-зависимостей — всё работает
локально.

## 1. Project overview

Приложение покрывает полный цикл продажи:

- приём входящих обращений (**Leads**) с сайта, по email, по телефону, по
  рекомендации или вручную;
- конвертацию лида в компанию (**Account**) и контактное лицо (**Contact**),
  опционально сразу со сделкой (**Opportunity**);
- ведение сделки по стадиям пайплайна с проверкой бизнес-правил при закрытии
  (won/lost);
- заметки и задачи (**Activity**) с дедлайнами и просроченными задачами;
- поиск и фильтры по всем ключевым сущностям;
- **Dashboard** с KPI и графиками (Chart.js), которые всегда считаются из
  актуального состояния базы.

## 2. Product legend

Агентство занимается выставочными стендами, пространствами и бренд-зонами.
Входящие обращения поступают с сайта, по email, по телефону, по рекомендации
или вносятся менеджером вручную. Продажа редко закрывается сразу: менеджер
квалифицирует лид (бюджет, площадка, сроки, формат работ), связывает его с
компанией и контактным лицом, создаёт сделку, ведёт её по стадиям, добавляет
заметки и задачи, закрывает сделку как выигранную или проигранную. Подробная
модель данных, справочники и бизнес-правила зафиксированы в [Plan.md](Plan.md).

`@prisma/adapter-pg`, без `PrismaPg`, без `prisma.config.ts` (эти три вещи
намеренно не используются в проекте).

## 4. Requirements

- Node.js 20+ и npm
- Docker Desktop (для локального PostgreSQL через `docker-compose.yml`) —
  либо любой другой доступный вам PostgreSQL 14+.

## 5. Installation

```bash
npm install
```

При установке Prisma и несколько других пакетов используют install-скрипты;
современный npm (11+) может запросить подтверждение через
`npm approve-scripts` — подтвердите его, иначе Prisma Client не сгенерируется.

## 6. Environment

Скопируйте `.env.example` в `.env` и при необходимости поправьте
`DATABASE_URL`:

```bash
cp .env.example .env
```

```
DATABASE_URL="postgresql://crmlite:crmlite@localhost:15432/crmlite?schema=public"
```

Реального `.env` в репозитории нет — только `.env.example`.

## 7. Database

Поднять локальный PostgreSQL через Docker (порт **15432** на хосте, чтобы не
конфликтовать с уже занятыми/зарезервированными портами):

```bash
docker compose up -d
```

Если вы используете собственный PostgreSQL — просто укажите его в
`DATABASE_URL` и пропустите `docker compose`.

## 8. Prisma

```bash
npm run db:generate        # сгенерировать Prisma Client
npm run db:migrate         # применить/создать migrations (prisma migrate dev)
npm run db:migrate:deploy  # применить существующие migrations без создания новых (CI/прод)
npm run db:seed            # заполнить БД демо-данными (prisma/seed.ts)
npm run db:reset           # migrate reset --force → пересоздаёт схему и автоматически сеет заново
npm run db:studio          # Prisma Studio — визуальный просмотр БД
```

`npm run db:reset` — основной воспроизводимый workflow для проверяющего:
полностью пересоздаёт схему и гарантированно заполняет её одним и тем же
детерминированным набором demo-данных.

## 9. Development

```bash
npm run dev
```

Приложение поднимется на `http://localhost:3000` и сразу перенаправит на
`/dashboard`.

## 10. Demo scenario

Полный acceptance-сценарий, от пустого действия до проверки dashboard:

1. `docker compose up -d` — поднять PostgreSQL.
2. `npm run db:reset` — пересоздать схему и засеять demo-данные.
3. `npm run dev` — запустить приложение.
4. Открыть **Leads** (`/leads`).
5. Нажать **+ Новый лид**, заполнить тему, контактное лицо, email/телефон,
   источник — создать лид.
6. Открыть карточку лида.
7. Нажать **Конвертировать лид** (Convert Lead) — заполнить компанию,
   контакт, при необходимости сделку.
8. Убедиться, что на карточке лида появились ссылки на созданные
   **Account**, **Contact** и **Opportunity**.
9. Открыть карточку **Account** → убедиться, что там виден новый **Contact**
   и новая **Opportunity**.
10. Открыть карточку **Opportunity** → изменить стадию (**Change Stage**).
11. Добавить **Note**.
12. Добавить **Task** с датой (**dueDate**).
13. Нажать **Выполнить** (**Mark as Done**) у задачи.
14. Попробовать отметить сделку как **выигранную** без суммы/контакта —
    убедиться, что сервер блокирует операцию понятным сообщением; заполнить
    сумму и контакт (Edit) — повторить, сделка закроется как WON.
15. На другой открытой сделке нажать **Отметить как проигранную** без
    причины — заблокировано; указать причину — сделка закроется как LOST.
16. Проверить поиск лидов (`/leads?search=...`), фильтры по source/status.
17. Проверить фильтры сделок по stage/status (`/opportunities?...`).
18. Открыть **Dashboard** (`/dashboard`).
19. Проверить KPI: Total Leads, Open Opportunities, Open Pipeline Value,
    Overdue Tasks.
20. Проверить графики: воронка сделок по стадиям, лиды по статусам.
21. Изменить любой Lead или Opportunity (например, ещё раз сменить стадию).
22. Повторно открыть **Dashboard**.
23. Убедиться, что показатели обновились и отражают новое состояние БД.

Этот сценарий полностью проверен вручную через реальный браузер (Playwright)
поверх реального PostgreSQL — включая проверку, что после смены состояния
данные на dashboard действительно пересчитываются (см. Plan.md, раздел 9).

## 11. Schema changes

1. Отредактируйте `prisma/schema.prisma`.
2. Создайте migration: `npx prisma migrate dev --name <описание>`.
3. Prisma Client перегенерируется автоматически; при необходимости —
   `npm run db:generate`.
4. Обновите связанные Zod-схемы (`src/lib/validation.ts`) и, если нужно,
   `src/lib/constants.ts` (labels/enum-списки).
5. При изменении demo-данных — обновите `prisma/seed.ts` и перепроверьте
   ожидаемые количества записей.

## 12. Testing

```bash
npm test          # vitest: Zod-схемы + бизнес-правила (реальный Postgres) + dashboard aggregation
npm run lint       # ESLint
npm run typecheck  # tsc --noEmit
npm run build      # next build (включает финальный typecheck)
```

`tests/business-rules.test.ts` — интеграционные тесты (реальная БД): convert
lead + запрет повторной конвертации, WON без суммы/контакта, LOST без
причины, complete task, соответствие dashboard-агрегаций прямым запросам к
БД. Тест сам создаёт и удаляет свои фикстуры — демо-данные не затрагиваются.

Автоматические тесты дополняют, но не заменяют ручной demo-сценарий выше.

## 13. Troubleshooting

- **`Error: P1001: Can't reach database server`** — проверьте, что
  `docker compose up -d` выполнен и `DATABASE_URL` в `.env` указывает на
  правильный порт (по умолчанию `15432`).
- **`npm install` зависает / просит подтверждения** — выполните
  `npm approve-scripts --allow-scripts-pending` и `npm rebuild`.
- **Порт 3000/15432 занят** — измените порт в `docker-compose.yml`
  (сервис `db`) и соответствующий `DATABASE_URL`, либо остановите процесс,
  занявший порт.
- **После `git pull`/смены схемы Prisma Client устарел** —
  `npm run db:generate`.
- **Хочу начать с чистого состояния** — `npm run db:reset`.

## 14. Known limitations

- `amount` в Opportunity хранится как целое число (рубли, без копеек) —
  осознанное упрощение для lite-CRM.
- Stage сделки не меняется автоматически при закрытии (won/lost) — сохраняет
  ту стадию, на которой сделка была закрыта; финальные статусы не
  дублируются как отдельные стадии.
- Нет аутентификации/ролей — CRM-lite рассчитана на одного менеджера/команду
  без разграничения доступа (вне рамок задачи).
- `package.json#prisma.seed` помечен Prisma как deprecated в пользу
  `prisma.config.ts`, но `prisma.config.ts` намеренно не используется —
  таково явное требование проекта. Предупреждение при запуске Prisma CLI —
  ожидаемо и безвредно.
- Воронка (`Opportunities by Stage`) на dashboard показывает только
  **открытые** сделки по стадиям — это осознанная интерпретация "воронки"
  как текущего активного пайплайна; выигранные/проигранные сделки видны в
  KPI, списках и карточках, но не дублируют стадии финальными состояниями.
